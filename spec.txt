1. Project Overview 
CivicConnect is a web-based civic issue reporting platform built for municipalities in Nepal. It provides a 
structured digital channel through which citizens can report local problems (road damage, water supply 
issues, sanitation, electricity, corruption, and so on) directly to the authority responsible for resolving 
them — their municipality admin. The platform is inspired by pratipakshya.org but scoped to the 
nagarpalika level so that every complaint has a clear, accountable recipient. 
The system is built around four roles — Guest, Citizen, Municipality Admin, and Super Admin — each with 
distinct capabilities enforced by a servlet filter. Complaints are public immediately after submission (no 
pre-approval queue), citizens can upvote any complaint across any municipality (national visibility), and 
each municipality's admin manages only their own municipality's complaints and users.

3. System Architecture 
The application follows the Model-View-Controller (MVC) pattern with supporting packages for DAO, 
service logic, utilities, and filters. HTTP requests enter through servlets (controllers), which delegate 
business logic to the service layer, which in turn uses DAO classes to read from and write to MySQL. 
Controllers then forward to JSP views that render the response. 
3.1 Request Lifecycle 
1. The browser sends an HTTP request to a URL (e.g., /citizen/submit-complaint). 
2. AuthFilter intercepts the request, checks session and role, and either allows the request to 
proceed or redirects to Login / Unauthorized pages. 
3. The matching Servlet (Controller) receives the request, extracts form parameters, and calls the 
appropriate Service method. 
4. The Service applies business rules (e.g., "only allow edit if status is Pending") and calls one or 
more DAO methods. 
5. Each DAO method opens a JDBC connection, executes a PreparedStatement, maps the result 
into a Model object, and closes the connection.

that removing a parent row automatically cleans up dependent rows (e.g., deleting a complaint removes 
all its votes). Status, role, and province are stored as VARCHAR columns with allowed values enforced in 
Java code (via constant classes) for flexibility.

4.3 Relationship Summary 
• One municipality has at most one active municipality_admin (strict 1:1) and many citizens. 
• One user (citizen) submits many complaints and may cast many votes (one vote per complaint). 
• One complaint belongs to exactly one category, one municipality, and one submitter user, and 
accumulates many votes. 
• Deleting a municipality cascades through its admin, citizens, complaints, and votes — but the 
platform avoids hard deletion of municipalities by offering only soft delete (deactivate) through 
the UI. 
4.4 Default Seed Data 
Only a minimal seed is inserted during initialization: 
• Nine complaint categories: Road/Infrastructure, Water Supply, Sanitation, Electricity, Health, 
Education, Corruption/Misconduct, Public Safety, Others. 
• One Super Admin account (email: admin@civicconnect.com, default password pre-hashed with 
BCrypt). 
• No municipalities, no municipality admins, and no citizens are pre-created — the Super Admin 
creates them after first login.

6. Authentication & Authorization 
6.1 Password Hashing 
All passwords are hashed using BCrypt before storage. BCrypt is the industry standard — it embeds a per-
user salt into the hash and is resistant to brute-force attacks thanks to its tunable work factor. At 
registration, the plaintext password is passed through BCrypt.hashpw() and the resulting hash is stored in 
users.password_hash. At login, BCrypt.checkpw() compares the entered plaintext against the stored hash. 
6.2 Session Management 
• Sessions are created on successful login using Java's built-in HttpSession. 
• Session attributes set after login: userId, userName, userRole, municipalityId (null for super 
admin), municipalityName, wardNumber (citizens only). 
• Session timeout is 60 minutes of inactivity (configured in web.xml via <session-timeout>). 
• On expiry, the next request is redirected to the Login Page with the message "Your session has 
expired. Please log in again." 
6.3 Remember Me Cookie

If the user checks Remember Me at login, a cookie storing only their email (never the password) is set 
with a 7-day expiry. On subsequent visits, the email field on the Login Page is pre-filled from this cookie. 
6.4 AuthFilter (Servlet Filter) 
The AuthFilter, configured in web.xml, intercepts every request to protected URLs (/citizen/*, /admin/*, 
/superadmin/*) and enforces role-based access control before any controller runs. 
Filter Decision Flow 
8. Is the URL public (home, login, register, about, CSS/JS/images)? → Allow through without 
checks. 
9. Does an HttpSession exist for the request? → If not, redirect to /login with message "Please log 
in to access this page." 
10. Read userRole from the session and check it against the URL prefix: 
◦ /citizen/* requires role = citizen 
◦ /admin/* requires role = municipality_admin 
◦ /superadmin/* requires role = super_admin 
11. Mismatch? → Redirect to /unauthorized (Unauthorized Access page). 
12. All checks pass? → chain.doFilter(request, response) lets the request proceed to the 
controller. 
6.5 Post-Login Role-Based Redirect 
After successful login, the Login servlet reads the user's role from the DB and redirects: 
• citizen → /citizen/dashboard 
• municipality_admin → /admin/dashboard 
• super_admin → /superadmin/dashboard 
6.6 Form Validation Strategy 
Validation happens at two layers. Client-side JavaScript gives instant feedback on field format (email 
shape, password strength, required fields) for better UX. Server-side Java validation in the Validator utility 
class is always the source of truth — the server never trusts client input and re-validates every field before 
it reaches the DAO layer. If any server-side check fails, the form is re-rendered with error messages and 
previously entered data retained (except password fields).

9.5 Updating Complaint Status 
The admin selects a new status and clicks Update. The complaints row is updated and updated_at is 
refreshed. The system confirms with "Complaint status updated to [New Status]." The citizen sees the

Lifecycle Rule

backwards, and a Resolved complaint cannot be reopened. If an issue recurs, a new complaint should be 
submitted.

14. Security Considerations 
• Password hashing — BCrypt with per-user salt embedded in the hash; never stored in plaintext. 
• SQL injection — every query uses PreparedStatement with parameter binding; string 
concatenation is forbidden. 
• XSS — JSP output uses JSTL's <c:out> tag or ${fn:escapeXml(...)}, which HTML-escapes user-
provided content by default. 
• CSRF — state-changing forms include a hidden CSRF token stored in the session; the servlet 
validates the token before processing. 
• Session hijacking — sessions use HttpOnly cookies; session IDs are regenerated on login. 
• File upload — uploads are validated by both MIME type and extension; filenames are 
randomized to prevent overwrite and directory traversal; files are stored outside /WEB-INF so 
JSPs cannot execute them. 
• Role enforcement — AuthFilter runs before every servlet reaches protected URLs; servlets 
additionally re-check session role and resource ownership (e.g., a citizen editing a complaint 
must own it). 
• Generic login errors — the login form never reveals whether the email or password was 
incorrect. 
• Deactivation vs deletion — destructive operations (municipality, admin, citizen) prefer 
deactivation over deletion to avoid irreversible data loss.

52. Super Admin logs in with seeded credentials.

54. Super Admin creates a Municipality Admin for each municipality (strict 1:1).

56. Municipality Admins log in and begin managing incoming complaints.
